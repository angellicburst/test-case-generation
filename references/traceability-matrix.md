# 需求追溯与待确认规范

追溯条目随用例一起生成，写入临时 IR 的 `traceability`，再渲染进各格式产物：Markdown 的 `## 需求追溯` / `### 需求追溯表` / 条件 `### 待确认项`，Excel 的 `需求追溯` / 条件 `待确认项` 工作表。**不生成、不交付独立的矩阵 JSON**；交付目录只保留 `.md` / `.xlsx`。

## 条目结构

```json
{
  "id": "TRACE-XXX-001",
  "source": "需求文档.md",
  "location": "2.1 示例章节",
  "rule": "满足条件时执行某行为并产生可观察结果",
  "status": "已覆盖",
  "case_ids": ["TC-XXX-001"]
}
```

| 字段 | 要求 |
| :--- | :--- |
| `id` | 文档内唯一，建议 `TRACE-{需求简写}-{流水号}` |
| `source` | 实际材料文件名；不得用需求编号或文件名以外的标识替代。用户补充确认的口径写 `用户补充确认`，`location` 注明确认日期与对话/材料位置 |
| `location` | 可定位的章节、表格行或流程节点；单行文本 |
| `rule` | 原文或不改变含义的摘要；必须写明适用条件、行为与可观察结果，不能只写功能概述；单行文本。同一材料的多条规则拆成多个条目 |
| `status` | `待覆盖`、`已覆盖` 或 `待确认` |
| `case_ids` | 关联用例 ID，按正文顺序；由 `render_cases.py` / `sync_artifacts.py` 从 `traceability_refs` 自动汇总，不手工维护 |
| `issue` / `assumption` / `question` | 未明确项、当前测试假设、待确认问题；仅 `待确认` 条目必填 |

## 状态与关联

- 起草时用 `待覆盖`；关联到用例后转 `已覆盖`；无法形成材料支持的确定预期时用 `待确认`。交付前不得残留 `待覆盖`。
- `已覆盖` 条目至少关联一条用例；`rule` 必须足以支撑其全部关联用例的确定性预期。
- `待确认` 条目不得被任何用例引用；`待覆盖` 可在起草时由用例引用，渲染/同步时自动转为 `已覆盖`。每条用例至少引用一个非待确认条目。
- 用例通过 `traceability_refs` 引用条目。引用顺序必须与追溯表行序一致；同一用例可关联多条规则。
- 删除用例后若某 `已覆盖` 条目失去全部关联，`sync_artifacts.py` 会报错阻断，需明确删除条目或调整用例，防止静默漏测。

## 跨格式一致性

- Markdown 的追溯表、Excel 的 `需求追溯` 表源自同一 IR，行序一致；两种格式的追溯表均至少需要 1 行有效数据，因此交付时至少存在 1 条 `已覆盖` 条目。
- 用例正文的引用、追溯表的 `关联用例` 列、Excel A 列必须互相对应。
- 两种格式交付后执行跨格式核对：

  ```bash
  python "{技能根目录}/scripts/validate_traceability_bundle.py" --markdown "<文件.md>" --excel "<文件.xlsx>" [--baseline "<ir.json>"]
  ```

  `--coverage-only` 只核应用例与覆盖是否一致，跳过格式细节；不带该参数时先执行两种格式的完整校验。

## 待确认项的记录与收敛

- 待确认条目只记录在产物内的 `待确认项` 中，汇报时提取展示，不另建清单，也不写成独立用例。
- 收敛标准、风险排序与每模块 3~5 项上限见[测试规则](test-rules.md#待确认项收敛与分级)。
- 用户确认后：补充或修改用例，将条目改为 `已覆盖` 并删除 `issue` / `assumption` / `question`；确认无需覆盖时删除条目及对应用例；随后重新渲染或同步并校验。
