# 需求追溯矩阵参考

每个需求在生成用例前创建 `需求追溯矩阵-{上线日期}-{需求名称}.json`，作为用例的长期追溯、覆盖和待确认数据源，并与用例一同保留。缺少上线日期且用户确认时，`{上线日期}` 写 `未指定日期`。

```json
{
  "entries": [
    {
      "id": "TRACE-001",
      "source": "需求文档.md",
      "location": "2.1 高危涉诈",
      "rule": "strategy_code=2204，十分钟线下核验及线下复机",
      "status": "已覆盖",
      "case_ids": ["TC-ONEKF-001"],
      "case_titles": ["高危涉诈按2204策略处理"]
    }
  ]
}
```

每个条目都必须包含：

- `id`：矩阵内唯一的追溯标识。
- `source`、`location`、`rule`：分别对应实际材料文件、可定位章节/表格行/流程节点，以及支撑用例的原文或不改变含义的摘要。`source` 必须填写实际材料文件，不得以正式需求编号或其他标识替代；唯一例外是用户补充确认的口径，写 `用户补充确认`。三个字段均为单行文本，不得包含换行；同一材料中的多条规则拆分为多个条目。摘要必须写明适用条件、行为与可观察结果，不能只写功能概述。
- `status`：`待覆盖`、`已覆盖` 或 `待确认`。建立矩阵时使用 `待覆盖`；主代理完成格式关联后改为 `已覆盖`；无法形成材料支持的确定预期时使用 `待确认`。
- `case_ids`、`case_titles`：分别关联 Excel 用例 ID 和 Markdown 用例标题。`已覆盖` 条目至少填写其中一项；本次交付的格式必须填写对应字段。同一用例可关联多个条目，用于验证多条需求规则。`已覆盖` 条目的 `rule` 必须足以支撑其关联用例的全部确定性预期；仅凭功能概述无法推出可观察结果的条目不得标记为 `已覆盖`。
- `issue`、`assumption`、`question`：分别为未明确项、当前测试假设和待确认问题，仅 `待确认` 条目必填。

`待覆盖` 和 `待确认` 条目不得关联用例。用户补充确认的口径使用 `source: "用户补充确认"`，`location` 写明确认日期与对话/材料位置。待确认条目不在 Markdown 或 Excel 中另存清单，汇报时从矩阵提取展示；用户确认后补充或修改用例并将条目改为 `已覆盖`，确认无需覆盖时删除该条目及相应用例。

Excel 输入 JSON 的每条用例填写 `traceability_refs` 数组，其成员必须是矩阵中 `已覆盖` 条目的 `id`。生成器将对应追溯按矩阵顺序渲染到备注开头的连续多行；不接收用例自身的自由追溯文本。Markdown 用例的标题与连续追溯引用也按矩阵顺序匹配。

各格式校验命令必须追加 `--traceability-matrix "<矩阵路径>"`。同时交付 Markdown 和 Excel 时，在两种格式均通过后执行 `validate_traceability_bundle.py --coverage-only` 核对矩阵关联与跨格式覆盖；不带该参数时脚本会重新执行两种格式校验。修改矩阵后，可用 `sync_traceability.py` 批量同步产物中的追溯文本；同步先写入同目录临时副本，正式文件替换失败时自动用备份恢复，回滚失败会保留备份并在报错中给出路径。随后重新校验，校验通过仍须人工核对矩阵内容与原始材料是否一致。
