# 测试用例规则参考

编写测试用例时遵循以下规则。本文件供 SKILL.md 步骤 3 引用。遵守 SKILL.md 中的需求完整性、材料冲突与交付流程。如本文件中的设计建议与所选格式规范冲突，格式规范决定字段、枚举、结构和渲染；但任何格式专属规则都不得要求补造材料未定义的产品行为。

## 用例优先级

优先级顺序：P0 > P1 > P2 > P3 > P4

| 级别 | 定义 | 占比（针对功能点） |
| :--- | :--- | :--- |
| P0 | 最基本的功能验证，用例不宜过多 | ~5% |
| P1 | 基本功能验证，可用于继承特性基本功能验证、迭代验收前基本功能验证 | ~20% |
| P2 | 重要特性验证，可用于测试版本（非回归版本）功能测试 | ~60% |
| P3 | 一般功能/非重要功能验证，包括对基本/重要功能的异常/回归测试 | ~10-15% |
| P4 | 非常特殊输入、场景、阈值条件的用例，不宜过多 | ~0-5% |

## 测试类型

| 一级类型 | 子类型/关注点 |
| :--- | :--- |
| 功能测试 | 正向测试、反向/异常测试、边界值分析、等价类划分、决策表测试、状态转换测试、场景/用例测试、错误推测法、接口参数、响应结构、错误码、幂等、数据一致性 |
| 回归测试 | 既有功能在新版本或改造后的回归验证、关联回归点、受影响行为验证 |
| 性能测试 | 负载测试、压力测试、稳定性/soak 测试、峰值/spike 测试、容量测试、并发测试 |
| 安全测试 | 渗透测试、漏洞扫描、认证测试、授权测试、输入验证测试、会话管理测试、加密测试、安全审计、CSRF/SSRF 测试、文件上传测试 |
| 兼容性测试 | 浏览器兼容性、操作系统兼容性、设备兼容性、网络兼容性、数据库兼容性、软件版本兼容、硬件兼容 |
| 易用性测试 | 用户体验测试、用户界面测试、导航测试、内容可读性、帮助系统测试、可访问性/无障碍测试、学习曲线评估 |
| 可靠性测试 | 容错测试、恢复测试、稳定性测试、故障转移测试、数据完整性测试、备份与恢复测试 |

## 功能点拆分与用例组织

- 功能模块包括进程、接口、页面、定时任务、报表或独立批处理任务。
- 同一功能模块中的多段业务逻辑属于同一功能点，例如同一预警处理进程内的扫描、工单生成、去重和历史迁移，应在该进程功能点下分别设计测试要点和用例；不要因内部逻辑不同拆为多个功能点。
- 只有可独立触发、独立交付或面向用户的模块不同，才拆分为不同功能点；例如数据同步进程与数据处理进程、查询接口与管理页面。
- 页面调用的内部接口随页面流程覆盖；仅在纯接口需求或接口独立于页面时单列接口功能点。
- 数据库字段、索引或迁移改动不得独立成功能点，必须结合使用该对象的业务逻辑设计；只有需求整体为纯数据/迁移需求（仅描述表结构或数据变化、不含任何进程/接口/页面/任务行为变化）时才可单列。
  - 数据库归并判定流程：列出改动对象（表/字段/索引）在需求中出现的全部使用方（进程、接口、页面、定时任务等）。
  - 存在使用方时，将字段定义、存量数据兼容、写入/读取、边界与失败场景作为该业务功能点下的测试要点或分组，不新增以“××表新增××字段”命名的顶层功能模块。
  - 无使用方且需求整体为纯数据/迁移时，才以数据操作本身为功能点。
  - 示例：需求“为表 A 新增字段 F，任务 T 成功后更新 F”时，字段 F 的场景归入任务 T 功能点；“仅将表 A 字段 X 长度由 20 调整为 50、无业务行为变化”可作为纯数据需求单列。
- “优化”或“改造”需求分别列出优化点与关联回归点；不受影响的点不写用例；关联回归点归入“回归测试”类型分组或用例，不得作为“功能测试”的子分组或用例。
- 同一功能点下的测试类型（功能测试、回归测试、性能测试、安全测试等一级类型）为同级分组，并列组织于功能模块下。
- 对有明确判定顺序的规则，先建立“规则优先级 → 测试分组”矩阵，再按业务优先级排列用例；不要按需求章节的出现顺序排列。每个判定条件独立成例；多个条件同时命中时，另设优先级冲突用例验证最高优先级结果。
- 涉及多个判定条件交叉作用时，提取条件组合建立判定逻辑，必须验证互斥场景与最高优先级生效逻辑，不得遗漏关键冲突路径。

## 测试设计能力

以下方法按材料明确内容与业务风险选用，不要求每条需求机械覆盖全部方法。

- **正向用例**：覆盖端到端标准流程、主干链路与典型有效数据，验证核心功能可用。
- **反向用例**：覆盖空输入、格式错误、超限输入、重复提交、未授权/越权、依赖服务超时/失败及并发冲突。
- **等价类划分**：根据材料识别有效与无效等价类；对材料明确规定的拒绝行为或已有可确认预期的无效类设计反向用例；每条反向用例只验证一个无效等价类（其他字段保持有效），防止多个非法条件相互掩盖；确需组合时按风险另行设计；不得为每种想象中的无效输入编造预期。
- **边界值分析**：针对数值、金额、长度、次数、时间等有界场景，必须覆盖临界值（刚好合法、刚好超限，即上点与离点），不得用普通中间有效值代替。
- **场景分析法**：构建用户旅程地图，覆盖典型端到端业务闭环、分支流和故障恢复流。
- **正交分解**：处理多参数组合场景。
- **判定表**：多规则互斥或叠加时，按条件组合梳理条件与动作。
- **状态迁移测试**：针对生命周期与状态机需求，覆盖材料明确规定的合法流转路径。只有材料明确规定非法跃迁应被拦截时，才将逆向跃迁、跨级跳转或终态再流转写为确定预期；未定义的路径与结果列入待确认清单，不自行补齐状态机规则。
- **页面功能覆盖**：按“入口与控件 → 枚举/默认值/必填性 → 选择或编辑 → 提交或查询结果 → 空值展示/回归”覆盖。对枚举值、状态、数据来源或不同入口，需求已明确且可独立判断时分别设计用例，不能以“任一”合并。

## 用例设计原则

- **精准**：
  - 测试用例表达用词要求精准。
  - 测试步骤、预期结果为必填项。
  - 前置条件需详细、简洁地说明执行测试前的准备事项，如被测对象所处状态、预置数据、预置条件等，不使用无用、抽象的条件。
  - 测试步骤中对必须的测试操作对象、操作方法需实例化表达清楚，非用例作者通过浏览也可以进行测试操作。
  - 步骤中有需要设置参数的要显示说明，不能只有“边界值”、“错误值”、“非法值”、“遍历所有字符”等简单描述。
  - 用例表述中不要使用模糊的、含二义性的语句，避免使用概数，如“很多”、“一些”、“部分”等。
  - 不要遗漏任何测试动作。
- **简洁单一**：
  - 测试用例表达要求简洁，测试逻辑单一。
  - 一个测试用例应覆盖单一测试逻辑。
  - 用例的执行步骤建议在7步以内，超过7步的考虑拆分为多个用例。
  - 对于产品技术、测试技术的基本知识和常识，不要在用例中描述。
  - 每个执行步骤建议描述单一的操作，应避免把多个复杂的操作放在同一步骤中。
  - 测试用例中不要写无关冗余的内容。
- **易懂**：
  - 测试用例表达用词要求易懂。
  - 测试用例从用户角度来描述，采用易于理解的自然语言，而避免太过专业化的用语，以保证不同技术层面的测试人员都能容易理解。
  - 避免出现对系统内部实现的描述。
- **易确认**：
  - 测试用例表达用词要求易确认。
  - 预期结果的描述尽量准确、具体、易确认、有代表性，可以清楚地判断测试失败还是成功，避免预期结果直接写“无错误”、“无异常”等笼统无法检查的描述。
  - 影响用例最终结果的检查点，需要填写预期结果，避免测试检查点遗漏；不得仅用笼统的“操作成功”作为可判定结果。
  - 预期结果中不能出现操作步骤，要将操作步骤和预期结果严格区分开。
- **风格一致**：
  - 测试用例表达用词要求风格一致。
  - 测试语法表达规则，即测试用例的表达须符合测试语法表达规则。
  - 测试逻辑与测试数据分离。
- **用词一致**：
  - 测试用例的表达必须使用相同的测试保留字。
  - 测试用例表达用词要求用词一致。
- **去重**：避免重复用例、完全等价的冗余用例。
- **一对一原则**：一个需求对应一个测试用例文档，不要把所有用例生成到一个测试用例文档中。
- **MECE 原则**：用例集合相互独立且完全穷尽。
- **相同逻辑不同入口用例规则**：针对需求中“相同处理逻辑”但“不同场景入口”的情况，如果没有特定强调只需要测试一处入口，那么需要对所有的入口设计测试用例。
- **分层验证断言规则**：预期结果以材料明确规定且测试环境可观测的业务表现和数据为准：
  - 展示与查询类：验证材料明确的界面行为、提示文案、状态码及响应报文属性；材料未说明的文案、状态码或属性不得自行假设。
  - 数据变更与流转类：验证材料提供的业务反馈，并在材料明确提供数据查询方式时断言相应持久化状态和关键字段；没有数据库/后台观测依据时，采用可用的业务查询或响应断言，并把持久化验证条件列为待确认项，不得编造表名或字段。
  - 异步任务与后台处理类：验证材料明确的任务终态及副作用；未提供观测方式或预期规则时记录待确认项，不虚构任务命令、目标表或副作用。
  - 解耦内部临时实现：中间临时过渡表、内部临时缓存变量等不作为验证对象，除非材料明确要求其沉淀或作为交付物。
- **性能场景规则**：性能测试应以需求给出的数据量、并发量、SLA 或容量目标设计。仅说明“大数据量”时，验证大数据量下处理可完成、结果正确且无明显异常，并将量化基线列为待确认项；不要编造单批大小、分片数量或告警阈值。
- **可执行数据与环境隔离规则**：
  - 前置条件必须描述能够构造的业务数据与初始环境状态（如账号处于正常状态、待处理记录初始为空）。
  - 占位符隔离性：数据准备示例必须使用具有独立隔离语义的脱敏占位符（如 `<新生成唯一流水号>`、`<独立测试账号>`），不得使用写死的主键常量，避免并发或多次执行时唯一约束冲突。一条示例只服务于一个判定条件；不要在产物中生成真实生产身份标识、手机号、账号或凭证。
  - 环境可重入与后置清理（Teardown）：凡用例操作修改了系统全局配置、占用了不可重用全局资源或产生破坏性环境变更，必须在预期结果末尾或步骤中注明后置恢复动作（如“恢复配置为默认值”、“清理测试临时占位资源”），确保测试用例具备可重复执行性。
- **多源材料基准规则（需求文档与设计文档）**：当输入同时提供需求文档与设计文档时，默认以需求文档定义业务范围、规则和验收标准，设计文档仅作实现细节补充，不得据此擅自扩大业务范围。若材料间存在影响范围或预期结果的冲突，记录冲突双方及影响并列入待确认清单；确认前不得把冲突中的任一说法写成无条件确定的预期。此规则适用于所有输出格式。
- **需求分析与测试假设规则**：
  - 需求输入材料不可避免地存在局部细节未交代或边界未详述的情况（如未定义特定异常的错误提示、未说明第三方超时重试机制、未给出具体性能量化SLA、未交代历史存量数据处理规则）。
  - 分级处理准则：核心主干业务缺失属于阻塞性问题，必须中断并向用户确认；局部细节模糊属于非阻塞性存疑，不得随意中断用例生成。
  - 假设使用边界：局部细节不完整时可记录测试假设以便评审，但不得将其写成需求事实或确定的产品预期。仅在假设依据合理且可写出条件式、可判定预期时，生成明确标记假设前提的用例；否则只记录待确认问题。
  - 存疑显式沉淀：将推导的假设统一沉淀为《需求存疑与待确认清单》，每个条目包含四要素：【涉及对象（功能模块/用例标题）、需求未明确项、当前测试假设、待产品/研发确认问题】。
  - 用例假设打标：仅对上述有依据且可判定的假设用例，在标题附加 `[待确认]` 并在预期结果或步骤中说明条件；不能形成明确预期时，只将问题写入待确认清单，不生成假设用例。
- **自动化测试就绪（Automation-Ready）规则**：用例步骤和预期结果应结构化、可执行、可判定。仅在需求材料、设计材料或用户补充明确提供时，填写 API 方法/路径/参数/响应断言、UI 控件标识/文案、后台命令/数据表字段等实现细节；示例只说明表达形式，不是产品事实。不得编造接口、控件、错误码、表名/字段、任务命令、具体提示文案或预期业务行为。信息不足时记录缺失项及其对执行/判定的影响；只断言材料支持且可观测的业务结果，无法确定预期时只记录待确认项，不生成伪确定用例。

## 执行准则

- **业务正向覆盖**：完整覆盖正常业务流程、关键用户旅程及合法输入组合，确保核心功能可用。
- **风险与逆向驱动**：充分挖掘边界极值、非法输入、权限越界、业务规则冲突、服务超时及并发竞争；用例分布由业务复杂度和质量风险决定，不设置机械的百分比比例。
- **覆盖边界与真实性**：只覆盖材料明确给出的业务规则、分支、约束和状态跃迁；不得为追求“全量覆盖”自行补齐未定义的状态、路径、阈值或预期结果。
- **需求追溯**：测试用例应覆盖材料中明确提出且适用的需求、业务规则、分支与约束；保留需求项到功能点、测试要点和用例的追溯关系，并标明未覆盖项及原因。不把无法枚举或材料未定义的内容宣称为“零遗漏”或“路径覆盖率 100%”。
- **补充用例**：仅在有需求依据或已明确标注并可判定的测试假设时，补充边界值与异常流场景；不为凑覆盖而编造竞品行为、系统响应或业务规则。
