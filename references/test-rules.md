# 测试用例规则参考

本文件是测试设计规则的唯一正文，由 `SKILL.md` 第 3 步引用。格式规范决定字段、枚举、结构与渲染；任何格式规则都不得要求补造材料未定义的产品行为。

## 用例优先级

P0 > P1 > P2 > P3 > P4

| 级别 | 定义 |
| :--- | :--- |
| P0 | 最基本的功能验证，用例不宜过多 |
| P1 | 基本功能验证，可用于继承特性基本功能验证、迭代验收前基本功能验证 |
| P2 | 重要特性验证，可用于测试版本（非回归版本）功能测试 |
| P3 | 一般功能/非重要功能验证，包括对基本/重要功能的异常/回归测试 |
| P4 | 非常特殊输入、场景、阈值条件的用例，不宜过多 |

## 测试类型

| 一级类型 | 子类型/关注点 |
| :--- | :--- |
| 功能测试 | 正向测试、反向/异常测试、边界值分析、等价类划分、决策表测试、状态转换测试、场景/用例测试、错误推测法、接口参数、响应结构、错误码、幂等、数据一致性 |
| 回归测试 | 既有功能在新版本或改造后的回归验证、关联回归点、受影响行为验证 |
| 性能测试 | 负载测试、压力测试、稳定性/soak 测试、峰值/spike 测试、容量测试、并发测试 |
| 安全测试 | 渗透测试、漏洞扫描、认证测试、授权测试、输入验证测试、会话管理测试、加密测试、安全审计、CSRF/SSRF 测试、文件上传测试 |
| 兼容性测试 | 浏览器兼容性、操作系统兼容性、设备兼容性、网络兼容性、数据库兼容性、软件版本兼容、硬件兼容 |
| 易用性测试 | 用户体验测试、用户界面测试、导航测试、内容可读性、帮助系统测试、可访问性/无障碍测试、学习曲线评估 |
| 可靠性测试 | 容错测试、恢复测试、稳定性测试、故障转移测试、数据完整性测试、备份与恢复测试 |

## 功能点拆分与用例组织

- 功能模块包括进程、接口、页面、定时任务、报表或独立批处理任务。同一模块内的多段业务逻辑（如同一预警进程内的扫描、工单生成、去重、历史迁移）属于同一功能点，在该功能点下分别设计测试要点，不因内部逻辑不同拆分；只有可独立触发、独立交付或面向用户的模块不同才拆分，例如数据同步与数据处理、查询接口与管理页面。页面调用的内部接口随页面流程覆盖，仅纯接口需求或接口独立于页面时单列。
- 数据库字段、索引或迁移改动不得独立成功能点，必须归入使用该对象的业务逻辑：
  - 列出改动对象（表/字段/索引）在需求中的全部使用方（进程、接口、页面、定时任务等）。
  - 存在使用方时，把字段定义、存量数据兼容、写入/读取、边界与失败场景作为该业务功能点的测试要点，不新增“××表新增××字段”式顶层模块。
  - 无使用方且需求整体为纯数据/迁移（仅描述表结构或数据变化）时，才以数据操作本身为功能点。
  - 示例：任务 T 成功后更新表 A 字段 F，字段 F 的场景归入任务 T；“字段 X 长度由 20 调整为 50、无业务行为变化”可单列。
- **纯发布配置与运维 DDL 豁免**：区分业务可测逻辑与纯上线发布配置、初始化字典 SQL、仅用于查询加速且无唯一约束语义的普通索引 DDL。除非需求明确将其列为测试验收项，不单独生成 `SHOW INDEX` / `SELECT` 查配置表类纯运维用例；相关影响归并到读写该表的业务功能点及回归验证。
- “优化/改造”需求分别列出优化点与关联回归点；不受影响的点不写用例；关联回归归入“回归测试”，不得嵌套为“功能测试”的子分组或用例。
- 同一功能点下的测试类型为同级分组。对有明确判定顺序的规则，先建立“规则优先级 → 测试分组”矩阵，再按业务优先级排列，不按需求章节顺序。每个判定条件独立成例；多条件同时命中时另设优先级冲突用例验证最高优先级结果；多条件交叉时建立判定逻辑，必须验证互斥场景。

## 测试设计能力

按材料明确内容与业务风险选用，不要求每条需求机械覆盖全部方法。

- **正向用例**：覆盖端到端标准流程、主干链路与典型有效数据。
- **反向用例**：仅对材料明确规定拒绝行为或已有可确认预期的场景，覆盖空输入、格式错误、超限、重复提交、未授权/越权、依赖超时/失败及并发冲突；未定义的异常行为不生成确定断言。
- **等价类划分**：识别有效与无效等价类；每条反向用例只验证一个无效等价类（其他字段保持有效），防止多个非法条件相互掩盖；确需组合时按风险另设；不为想象中的无效输入编造预期。
- **边界值分析**：针对数值、金额、长度、次数、时间等有界场景，必须覆盖临界值（刚好合法、刚好超限，即上点与离点），不得用普通中间有效值代替。
- **场景分析法**：构建用户旅程地图，覆盖典型端到端闭环、分支流与故障恢复流。
- **正交试验**：处理多参数组合场景。
- **判定表**：多规则互斥或叠加时，按条件组合梳理条件与动作。
- **状态迁移测试**：覆盖材料明确规定的合法流转路径；只有材料明确规定非法跃迁应被拦截时，才把逆向跃迁、跨级跳转或终态再流转写为确定预期。
- **页面功能覆盖**：按“入口与控件 → 枚举/默认值/必填性 → 选择或编辑 → 提交或查询结果 → 空值展示/回归”覆盖；枚举值、状态、数据来源或入口可独立判断时分别设计，不以“任一”合并。

## 用例设计原则

- **精准**：用词精准；测试步骤、预期结果必填；前置操作说明被测对象状态、预置数据与预置条件，不用无用、抽象的条件；步骤可被非作者复现，参数取值写明，不用“边界值/错误值/非法值/遍历所有字符”等笼统描述；不用“很多/一些/部分”等概数；不遗漏测试动作。
- **简洁单一**：单一测试逻辑；步骤建议 ≤7 步，超出拆分；每步尽量只描述一个操作；不写产品/测试常识与冗余内容。
- **易懂**：从用户角度、用自然语言描述，不同技术层面均可理解。
- **易确认**：预期结果准确、具体、可判定，不写“无错误/无异常/操作成功”等笼统结论；影响最终结果的检查点不得遗漏；步骤与预期严格分开。
- **一致**：术语与风格统一，测试逻辑与测试数据分离。
- **去重与 MECE**：无重复或完全等价用例；用例集合相互独立且完全穷尽。
- **相同逻辑不同入口**：未特指只测一处时，所有入口均需设计用例。

## 前置操作与后置操作

- 前置操作既包含数据/环境构造动作，也包含执行前必须满足的环境与数据状态；状态类前提直接陈述即可，不强求为静态前提硬凑动词。
- 后置操作独立成字段/列。需要恢复环境或清理脏数据时写入后置操作，**严禁重复写进测试步骤**；除非撤销/回滚本身就是被测业务功能。

## 断言与分层验证

预期结果只写材料明确且测试环境可观测的业务表现与数据：

- **展示与查询**：界面行为、提示文案、状态码、响应报文属性；材料未说明的不自行假设。
- **数据变更与流转**：业务反馈；材料提供查询方式时断言持久化状态与关键字段；无数据库/后台观测依据时用可用的业务查询或响应断言，不编造表名、字段。
- **异步任务与后台处理**：任务终态及材料明确的副作用；未提供观测方式或预期规则时记待确认，不虚构命令、目标表或副作用。
- **内部实现分层**：
  - 前端页面/用户交互类：面向用户视角描述入口、控件操作与可见反馈，不暴露未定义的内部实现。
  - 后台任务/批处理/接口/数据流转类：直接使用材料明确提供的表名、字段名、枚举值、API 路径与定时任务命令，确保可执行、可断言；仍禁编造中间临时表或缓存。
  - 中间临时过渡表、内部临时缓存不作为验证对象，除非材料明确要求其沉淀或作为交付物。
- **性能场景**：按需求给出的数据量、并发量、SLA 或容量目标设计。仅说明“大数据量”时，验证处理可完成、结果正确且无明显异常，并记录量化基线待确认；不编造单批大小、分片数量或告警阈值。

## 数据与环境隔离

- 前置操作必须能构造出所需业务数据与初始环境状态（如账号正常、待处理记录为空）。
- **占位符隔离**：使用具有独立隔离语义的脱敏占位符（如 `<新生成唯一流水号>`、`<独立测试账号>`），不用写死主键常量，避免并发或多轮执行唯一约束冲突；一条示例只服务一个判定条件；产物中不得出现真实生产身份标识、手机号、账号或凭证。
- **环境可重入**：修改全局配置、占用不可复用资源或产生测试数据时，说明恢复或清理要求，避免影响其他用例与重复执行；被测业务自身的撤销/回滚属于测试步骤。

## 多源材料与真实性

- **多源材料基准**：同时提供需求与设计文档时，以需求文档定义业务范围、规则和验收标准，设计文档仅补充实现细节，不得据此扩大范围。材料冲突时记录双方及影响，确认前不得把任一方写成无条件确定的预期；适用于所有格式。
- **需求分级**：核心主干业务缺失属阻塞，必须中断确认；局部细节模糊（异常文案、超时重试、边界默认值、存量兼容等）属非阻塞，可继续有依据的用例，但不得写成需求事实或确定预期。
- **预期回溯**：逐条确认每个确定预期都能回溯到该用例关联的 `已覆盖` 条目，其适用条件、行为与可观察结果均见于 `rule`；不能回溯的删除断言或转为待确认，不得借同模块其他规则或常识补齐。
- **自动化就绪**：步骤与预期结构化、可执行、可判定；仅在材料或用户补充明确提供时填写 API 方法/路径/参数/响应断言、UI 控件标识/文案、后台命令/数据字段。信息不足时记录缺失项及其影响，只断言材料支持且可观测的结果。

## 待确认项收敛与分级

- 只有缺失信息直接影响主判定分支、核心边界的含/不含口径、关键外部依赖的异常/超时降级、核心落库结果，或材料之间存在冲突时，才记入 `待确认`。
- 不对材料未提及的纯运维 SQL、常规非核心字段、次要基础设施异常主动发散。
- 条目按风险从高到低排序；单模块常规需求原则上收敛在 **3~5 项以内**。
- 记录与展示按[需求追溯与待确认规范](traceability-matrix.md)：写入产物内的 `待确认项`，汇报时提取展示，不另建清单。

## 用例 ID 稳定策略

- 格式 `TC-{需求简写}-{3 位流水号}`；需求简写由 LLM 从需求名称核心词提炼 2~8 位大写字母/数字，单需求文档统一前缀，不绑定模块名。
- ID 是永久主键而非展示行号：删除允许跳号；新增分配现有最大值 + 1。
- 仅评审定稿/提测前允许 `--renumber` 原子重排；不传 `--id-prefix` 时按各自已有前缀独立计数防冲突，显式传参才统一覆盖。进入执行或缺陷跟踪阶段后禁止重排。

## 元数据交互

- 缺失上线日期、输出目录（项目无 `03-TCD` 约定时）与其他确认项合并为一次提问。
- 用户明确希望直接出稿且未给日期时，允许以 `未指定日期` 先行起草，并在汇报中说明。
- 同名同格式文件的覆盖确认底线不变：未确认不得写入。

## 确认维护

- 用户确认回复包含多个并列子条件（如“无记录 / 字段为空 / 查询超时”）时，逐项拆解并落到用例。
- 边界上点口径确认后，同步检查既有离点用例是否紧邻新边界（如“正好 6 个月”对应离点“6 个月零 1 天”）。
- 确认的规则转 `已覆盖` 并补齐两种格式关联；无需覆盖的条目及对应用例删除；保持用例数量、追溯文本与两种格式一致。

## 执行准则

- **业务正向覆盖**：完整覆盖正常流程、关键旅程与合法输入组合。
- **风险与逆向驱动**：挖掘边界极值、非法输入、权限越界、规则冲突、服务超时与并发竞争；用例分布由业务复杂度与风险决定，不设机械比例。
- **覆盖边界与真实性**：只覆盖材料明确的规则、分支、约束与状态跃迁，不为“全量覆盖”自行补齐未定义内容。
- **需求追溯**：保留材料到用例的追溯关系，不宣称“零遗漏”或“路径覆盖率 100%”。
- **补充用例**：仅在需求有依据时补充边界与异常；不为凑覆盖编造竞品行为、系统响应或规则。
